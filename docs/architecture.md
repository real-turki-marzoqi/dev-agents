# نظام فريق التطوير الآلي — من فكرة HTML إلى Skill حقيقي في Claude Code

> توثيق كامل لفكرة المشروع المستخرجة من `dev-team-system (2).html`
> + تحليل هندسي واقعي: وش ينفع كما هو، وش لازم يتعدّل، وكيف نبنيه فعلياً.

---

## ١ — الفكرة في سطر واحد

**فريق برمجي كامل من وكلاء متخصصين داخل Claude Code:** تكتب فكرتك بالعربي بأمر واحد
(`/run-task`)، الفريق يخطّط ويتناقش ويبرمج ويختبر ويوثّق — وتدخّلك البشري **مرة واحدة فقط**
عند اعتماد التاسك.

### المشكلة اللي يحلها

| قبل | بعد |
|---|---|
| تنظّم التاسك يدوياً وتعيد شرحه لكل خطوة | أمر واحد يشغّل الدورة كاملة |
| موافقة على كل أمر تنفيذي (ضياع وقت) | صلاحيات معرّفة مسبقاً في `settings.json` |
| نفس النموذج يكتب الكود ويختبره ويراجعه (تحيّز) | أدوار معزولة السياق تراجع بعضها |
| لا ذاكرة — كل تاسك يبدأ من الصفر | ذاكرة ملفّية تتراكم عبر التاسكات |

## ٢ — المخطط الكامل كما في التصميم الأصلي

### فيز ١ · التخطيط — «تدقيق التخطيط أرخص من تدقيق الكود»

| # | الدور | النوع | الوظيفة |
|---|---|---|---|
| ؟ | أسئلة الفهم | تدخّل بشري خفيف | سؤال–سؤالين قبل أي شغل للتأكد من الفهم |
| ١ | المحلل | وكيل | يحوّل الفكرة الخام إلى حل مقترح + سكوب |
| ٢ | مراجع الحل · مراجع الممارسات · وكيل التقنيات | بوابات (بالتوازي) | ثلاثة آراء مستقلة؛ الاعتراض يرجع للمحلل — سقف **٥ دورات** |
| ⎙ | حزم القرارات | نقطة | يكتب `decisions.md` النظيف من أرشيف `discussion.md` |
| ٣ | وكيل نوشن | وكيل | يسجّل التاسك المنظّم في Notion عبر MCP |
| ٤ | مدقّق صياغة نوشن | بوابة | يتأكد أن التاسك المكتوب يعكس القرارات |
| ◑ | فريق قرار التصميم | بوابة شرطية | لو فيه UI: وكيل الهوية + وكيل UX يتناقشان → `design.md` |
| ★ | **مراجعتك أنت** | تدخّل بشري إجباري | نقطة الاعتماد الوحيدة — قبل أي سطر كود |
| ◆ | نقطة حرجة ١ | فحص | حفظ الحالة + تحديث الذاكرة |

| # | الدور | النوع | الوظيفة |
|---|---|---|---|
| ٥ | المطوّر | وكيل | ينفّذ ضمن السكوب المعتمد فقط |
| ◐ | المصمّم | وكيل شرطي (بالتوازي) | ينفّذ الاستايل من `design.md` حرفياً |
| ◑ | مدقّق مطابقة التصميم | بوابة | يقارن التنفيذ بـ `design.md` |
| ٦ | كاتب التيستات | وكيل مستقل | يكتب الاختبارات — منفصل عن كاتب الكود |
| ▶ | طبقة التست | بوابة حاسمة | تشغيل فعلي → `PASS / FAIL` |
| ٧ | بوابات المراجعة الست | بوابات | الجودة · الأداء · الأمان · UX · الناقد العدائي · التوافق |
| ٨ | المنسّق (الحسم + الرجوع الذكي) | موجّه | يصنّف الفشل ويرجّعه للمرحلة الصح، مو دائماً للمطوّر |
| ◆ | نقطة حرجة ٢ | فحص | كل البوابات PASS → حفظ + ذاكرة |

### فيز ٣ · التوثيق

| # | الدور | الوظيفة |
|---|---|---|
| ٩ | كاتب التوثيق | docstrings · README · شرح القرارات المعمارية |
| ◷ | مراجع التوثيق | يتأكد أن التوثيق مطابق للكود الفعلي |
| ◆ | نقطة حرجة ٣ | خلاصة التاسك للذاكرة + تحديث Notion إلى `Done` |

### الطبقات الداعمة

| الطبقة | الملف / الآلية | الغرض |
|---|---|---|
| أرشيف النقاش | `discussion.md` | محضر كامل لكل دورة: مين اقترح، مين اعترض، وش انحزم |
| القرارات | `decisions.md` | المخرج النظيف الذي يُبنى منه التاسك |
| الهوية البصرية | `design.md` | المرجع الوحيد للمصمّم ومدقّق المطابقة |

| الصلاحيات | `.claude/settings.json` | allow واسع + deny صغير (`rm -rf` · `git push` · قراءة `.env`) |

## ٣ — التحليل الذكي: وش واقعي ووش يحتاج إعادة تصميم

هذا أهم قسم. الفكرة ممتازة معمارياً، لكن فيها **٧ نقاط اصطدام** مع الواقع التقني
لـ Claude Code لازم تنحل قبل ما تصير Skill شغّال:

### ✅ ٣.١ — ما هو مدعوم فعلاً وجاهز

| العنصر في الفكرة | الآلية الحقيقية في Claude Code |
|---|---|
| وكلاء بأدوار وسياق معزول | Subagents في `.claude/agents/*.md` (frontmatter: `name` · `description` · `tools` · `model`) |
| تشغيل وكلاء بالتوازي | استدعاءات `Task/Agent` متعددة في رسالة واحدة |
| أمر واحد يشغّل الدورة | Skill في `.claude/skills/run-task/SKILL.md` يُستدعى بـ `/run-task` |
| الصلاحيات الواسعة + قائمة المنع | `permissions.allow` / `permissions.deny` في `settings.json` — تعمل كما هي في الصفحة |
| ملفات الحالة والذاكرة | ملفات عادية داخل الريبو — لا تحتاج أي ميزة خاصة |
| Notion | Notion MCP connector — موجود ويشتغل |

### ⚠️ ٣.٢ — نقاط الاصطدام والحلول

#### (١) الوكيل الفرعي **ما يقدر يكلّمك**
أكبر فجوة في التصميم الأصلي: «المحلل يسألك سؤالين» و«مراجعتك على نوشن» مرسومة كأنها
داخل الوكلاء. الواقع: الـ subagent يشتغل معزول ويرجّع تقرير نهائي — **ما عنده قناة للمستخدم**.

**الحل:** كل تفاعل بشري يصير عند **المنسّق (الجلسة الرئيسية)** نفسه:
- أسئلة الفهم → المنسّق يسألها بـ `AskUserQuestion` **قبل** إطلاق المحلل.
- اعتماد التاسك (★) → المنسّق يعرض ملخّص `decisions.md` ويوقف بـ `AskUserQuestion`
  (اعتماد / تعديل / إلغاء).

> النتيجة: المنسّق ليس وكيلاً رقم ٨ — هو **الـ Skill نفسه** الذي يعيش في الجلسة الرئيسية
> ويدير كل الوكلاء. هذا تبسيط يقوّي التصميم، ما يضعفه.

#### (٢) خمسة عشر وكيلاً = تكلفة توكنز انفجارية
٦ بوابات مراجعة × ١٠ دورات محتملة × سياق الكود كامل لكل بوابة = تاسك واحد ممكن يحرق
ملايين التوكنز. فريق حقيقي ما يسوّي code review كامل بعد كل سطر.

**الحل — دمج ذكي بلا خسارة أدوار:**

| الأصل (١٥+ دور) | المقترح (٩ وكلاء) |
|---|---|
| مراجع الحل + مراجع الممارسات + وكيل التقنيات | `plan-reviewer` واحد بثلاث عدسات **+ ** `critic` عدائي مستقل (رأيان يكفيان للاستقلالية) |
| وكيل نوشن + مدقّق صياغة نوشن | `notion-scribe` واحد + فحص ذاتي ببنية checklist |
| وكيل الهوية + وكيل UX + وكيل الاعتماد | `design-lead` واحد يُخرج `design.md` |
| البوابات الست | `code-reviewer` (جودة+أداء+توافق) و `security-reviewer` (أمان+ثغرات) — والدورة **الأولى فقط** تشغّل الاثنين، دورات الإصلاح تراجع الـ diff فقط |
| طبقة التست | **ليست وكيلاً أصلاً** — انظر النقطة (٤) |

القاعدة: **الاستقلالية تجي من عزل السياق، مو من كثرة الوكلاء.** وكيلان مستقلان بعدسات
مختلفة يعطيان ٩٠٪ من فائدة ستة، بربع التكلفة.

#### (٣) الحلقات وسقوفها ما تنضبط بالنوايا
«سقف ٥ دورات» المكتوب في برومت ينتهك بسهولة — النموذج ينسى العدّ في السياقات الطويلة.

**الحل:** الحالة تعيش في **ملف، مو في ذاكرة النموذج**:

```json
// tasks/<task-id>/state.json
{
  "phase": "planning",
  "planning_round": 2,
  "coding_round": 0,
  "gates": { "tests": null, "code_review": null, "security": null },
  "approved_by_human": false
}
```

الـ Skill يُلزم المنسّق: اقرأ `state.json` قبل كل خطوة، حدّثه بعدها.
تجاوز السقف → إيقاف إجباري وتقرير للمستخدم. وهذا يعطيك مجاناً ميزة **الاستئناف**:
انقطعت الجلسة؟ `/run-task --resume` يكمل من آخر حالة محفوظة.

#### (٤) بوابة التست لازم تكون **حتمية، مو رأي وكيل**
وكيل «يشغّل التيستات ويقول نجحت» ممكن يهلوس النجاح. أقوى قرار في التصميم كله:

**الحل:** المنسّق يشغّل `npm test` (أو أمر المشروع) **بنفسه عبر Bash** ويقرأ exit code.
`0` = عبور، غيره = فشل مع اللوق الخام يُمرَّر للمطوّر. صفر اجتهاد، صفر هلوسة.
وممكن تعزيزها بـ **hook** (`PreToolUse` على `git commit`) يمنع أي كوميت قبل نجاح التست —
حاجز على مستوى الـ harness نفسه لا يستطيع أي وكيل تجاوزه.

#### (٥) `agent-memory` ليست ميزة مدمجة — لكن بناءها تافه
لا يوجد شيء اسمه `.claude/agent-memory/` مدمج في Claude Code.

**الحل:** مجلد ملفات عادي، ملف لكل دور، والـ SKILL.md يلزم كل وكيل بسطرين في برومته:
> «قبل البدء اقرأ `memory/<role>.md`. قبل التسليم أضف أقصى ٣ دروس جديدة غير مكررة.»

مع قاعدة تنظيف: تجاوز الملف ١٥٠ سطراً → الوكيل يلخّصه في نفس الجولة. يُحفظ في git
فيصير الفريق «يتعلّم» فعلاً عبر التاسكات — بالضبط كما تخيّلته الصفحة، بدون أي ميزة سحرية.

#### (٦) Notion لازم يكون **اختيارياً**
لو الـ MCP غير متصل أو تعطّل، ما يصح يموت التدفّق كله.

**الحل:** الـ scribe يكتب دائماً `task.md` محلياً (مصدر الحقيقة)، ثم **يحاول** المزامنة
مع Notion. فشلت؟ يسجّل تحذيراً ويكمل. نقطة الاعتماد البشري تعرض المحتوى المحلي.

#### (٧) الرجوع الذكي يحتاج **تصنيفاً مكتوباً، مو حدساً**
«يوجّه الفشل للمرحلة الصح» يشتغل فقط لو أعطينا المنسّق جدول قرار صريح في SKILL.md:

| نوع الفشل | يرجع إلى |
|---|---|
| تست فشل والكود سبب واضح | `developer` (diff فقط، مو إعادة كتابة) |
| تست فشل والتغطية ناقصة | `test-writer` |
| اعتراض معماري / السكوب غلط | حلقة التخطيط (`analyst`) — **ويُصفَّر** عداد الكود |
| ثغرة أمنية حرجة | **إيقاف + إشعار المستخدم** (أحد استثنائي الرجوع للبشر) |
| عدم مطابقة تصميم | `designer` |

## ٤ — البنية النهائية القابلة للتنفيذ

```
project-root/
├── .claude/
│   ├── settings.json              # الصلاحيات (كما في الصفحة الأصلية — صحيحة)
│   ├── skills/
│   │   └── run-task/
│   │       └── SKILL.md           # المنسّق: التدفّق كامل + جدول الرجوع + السقوف
│   ├── agents/
│   │   ├── analyst.md             # المحلل
│   │   ├── plan-reviewer.md       # مراجعة الحل + الممارسات + الستاك (٣ عدسات)
│   │   ├── critic.md              # الناقد العدائي (تخطيطاً وكوداً)
│   │   ├── design-lead.md         # قرار الهوية البصرية → design.md (شرطي)
│   │   ├── notion-scribe.md       # task.md محلياً + مزامنة Notion
│   │   ├── developer.md           # التنفيذ ضمن السكوب
│   │   ├── test-writer.md         # اختبارات مستقلة
│   │   ├── code-reviewer.md       # جودة + أداء + توافق
│   │   ├── security-reviewer.md   # أمان + صلاحيات + تسريب
│   │   └── doc-writer.md          # توثيق + مطابقة ذاتية للكود
│   └── tasks/                     # حالة وأرشيف كل تاسك
│       └── <task-id>/
│           ├── state.json         # الحالة — مصدر الحقيقة للحلقات والسقوف
│           ├── discussion.md      # محضر النقاش (كل دورة)
│           ├── decisions.md       # القرارات النهائية
│           ├── design.md          # الهوية البصرية (لو UI)
│           └── task.md            # التاسك المنظّم (مرآة Notion)
└── memory/                        # ذاكرة الفريق — ملف لكل دور، في git
    ├── analyst.md
    ├── developer.md
    └── ...
```

### هيكل `SKILL.md` (المنسّق) — الجوهر

```markdown
---
name: run-task
description: >
  Full autonomous dev-team pipeline: plan → review loop → human approval
  → code → adversarial gates → docs. Invoke with the task idea as args.
---

# Dev Team Orchestrator

You are the COORDINATOR. You never write code yourself — you route work
between subagents and enforce the state machine below.

## Hard rules
1. Read/update `tasks/<id>/state.json` before/after EVERY step.
2. Planning loop cap: 5. Coding loop cap: 10. On cap hit → STOP, report.
3. Run tests YOURSELF via Bash; trust exit codes only, never agent claims.
4. Exactly ONE mandatory human stop: present decisions.md + design.md
   via AskUserQuestion (approve / edit / cancel) before any code.
5. Ask 1–2 clarifying questions FIRST, before launching the analyst.

## Phase 1 — Planning
analyst → (plan-reviewer ∥ critic) → objections? back to analyst
→ agreed: write decisions.md → design-lead (UI only) → notion-scribe
→ ★ HUMAN APPROVAL → checkpoint: save state + update memory/

## Phase 2 — Code
developer (∥ designer if UI) → test-writer → RUN TESTS (Bash)
→ (code-reviewer ∥ security-reviewer) on first pass; diff-only re-reviews
→ route failures per the routing table → checkpoint 2

## Failure routing table
| failure | route to |
|---|---|
| test fails, code bug        | developer (diff-scoped fix) |
| missing test coverage       | test-writer |
| architectural objection     | analyst (reset coding counter) |
| critical security issue     | STOP + notify user |

## Phase 3 — Docs
doc-writer → verify docs match code → mark task Done (local + Notion)
→ final summary to user
```

### مثال وكيل — `developer.md`

```markdown
---
name: developer
description: Implements the approved scope from decisions.md. Never expands scope.
tools: Read, Edit, Write, Grep, Glob, Bash
---

Before starting: read `tasks/<id>/decisions.md` and `memory/developer.md`.
Implement ONLY what decisions.md specifies. Match existing code style.
If UI work exists, follow `design.md` exactly — never improvise styling.
On finish: append up to 3 new non-duplicate lessons to `memory/developer.md`.
Return: list of changed files + a summary of what was implemented.
```

### `settings.json` — كما في الصفحة، مع إضافة واحدة

```json
{
  "permissions": {
    "allow": [
      "Edit", "Write", "Read",
      "Bash(npm test:*)", "Bash(npm run:*)",
      "Bash(git diff:*)", "Bash(git add:*)", "Bash(git status:*)"
    ],
    "deny": [
      "Bash(rm -rf:*)", "Bash(git push:*)",
      "Read(./.env)", "Read(./.env.*)", "Read(**/*.key)", "Read(**/secrets/**)"
    ]
  }
}
```

## ٥ — خطة التنفيذ المرحلية (ابدأ صغيراً، وسّع بثقة)

| المرحلة | المحتوى | معيار النجاح |
|---|---|---|
| **MVP — أسبوع** | المنسّق + ٤ وكلاء فقط: `analyst` · `developer` · `test-writer` · `code-reviewer` + نقطة الاعتماد + `state.json` | تاسك حقيقي صغير يمر من الفكرة للكود المختبَر بتدخّل واحد |
| **V2** | إضافة `critic` و `security-reviewer` وجدول الرجوع الذكي + طبقة الذاكرة | فشل تست يُوجَّه تلقائياً للجهة الصح |
| **V3** | `notion-scribe` + طبقة التصميم الشرطية (`design-lead` + `designer`) + `doc-writer` | الدورة الكاملة الثلاثية كما في المخطط الأصلي |
| **V4 — تحسين** | hooks لحراسة الكوميت + `--resume` + ضغط الذاكرة الدوري | نظام يشتغل يومياً على مشاريعك الفعلية |

> **ليش بهذا الترتيب؟** كل نقطة اصطدام في القسم ٣ تُختبر مبكراً بأرخص نسخة.
> لو الـ MVP أثبت إن الحلقة developer↔tests تتقارب فعلاً، الباقي إضافات آمنة.

## ٦ — تقييم صادق

| المعيار | التقييم |
|---|---|
| الجدوى التقنية | **عالية** — كل مكوّن يستند لميزة موجودة فعلاً (subagents · skills · permissions · hooks · MCP) |
| أقوى فكرة في التصميم | فصل «كاتب الكود» عن «كاتب التست» عن «المراجع» + الرجوع الذكي للمرحلة الصح |
| أكبر خطر | تكلفة التوكنز لو طُبّقت الـ ١٥ وكيلاً حرفياً — **الدمج إلى ٩ ضروري، مو اختياري** |
| ثاني أكبر خطر | حلقات لا تتقارب — يحلّها `state.json` + السقوف الملفّية |
| الفرق الجوهري عن الصفحة | التفاعل البشري كله عند المنسّق (الجلسة الرئيسية)، والتست حتمي عبر Bash |
| هل تستحق البناء؟ | **نعم** — بشرط البدء بالـ MVP رباعي الوكلاء، لا بالنظام الكامل |
